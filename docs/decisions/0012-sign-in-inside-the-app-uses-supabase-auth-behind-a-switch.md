# Sign-in inside the app uses Supabase Auth, behind a switch

## In plain words

Today a Cloudflare page asks for your email and sends you a code before you can see the site. That works for a small team but not for the public. We built the app's own sign-in (accounts, passwords, email codes, confirmation emails in our own design) on Supabase, which we already use for the database. It is switched off. The team site keeps working exactly as before until the owner flips one setting.

## Context

The owner asked for a full login, email confirmation, our own designed emails, a clear place in the repo for sign-in and email, and settings kept to the bare minimum. The site will become public later, so the login must work for people outside the team, not only for a fixed list of emails.

We looked at three options:

| Option | Cost now | Fits a public app | Extra service |
| --- | --- | --- | --- |
| Keep only the Cloudflare login | Free | No: it is a gate for known emails, not accounts | No |
| Supabase Auth | Free (50,000 monthly users on the free plan) | Yes | No, already our database |
| A separate login provider | Free at first, paid later | Yes | Yes |

Supabase Auth wins because the database already checks every read against the team list using the signed-in email (row level security), so a Supabase login plugs straight into rules that exist. A separate provider would need a bridge to the database and one more account to look after.

## Decision

1. Sign-in uses Supabase Auth: email and password, or a one-time code by email. An email must be confirmed before anyone can sign in.
2. Everything about sign-in and email lives in the top-level `auth/` folder ([auth/README.md](../../auth/README.md)): one HTML and one plain-text file per email, a shared layout and parts, a build script, a preview page, and a script that sends the templates to Supabase. The app code lives in `web/src/auth/`.
3. Every email link opens a page in the app that asks for one click before it uses the link. Some mail filters open every link to scan it, which would use up a one-time link before the person can.
4. In-app sign-in is off unless the site is built with `VITE_APP_AUTH=on`. When it is off, none of the sign-in code is downloaded and the Cloudflare login is the only gate.
5. When it is on, the app shows its own sign-in until there is a session with a confirmed email that is on the team list. The database keeps checking the team list on every read, so the screen is about what people see, not what they can fetch.
6. Settings keep two sections only: Account (email, password, sign out, a request to delete the account) and Appearance (theme). The other sections are hidden, not deleted, and come back by adding them to the menu.
7. Nothing live changed in this step. No key was created and no Supabase or Cloudflare setting was touched.

## Consequences

- The two logins can run together. Keeping Cloudflare in front while in-app sign-in is on means two sign-ins for the team, but the data files stay private. The site's research data is still copied into the site as files, so before Cloudflare is removed for a public launch, those files must move behind the database or a server check.
- Supabase's built-in email sender only delivers to members of the Supabase organisation and only 2 emails an hour. Real use needs our own email provider (options and prices are in [auth/README.md](../../auth/README.md)).
- To switch on, the owner must: create a Supabase access token and store it in the Keychain, run `auth/push_templates.sh --apply --settings`, choose and connect an email provider, move `auth/sql/0001_verified_members_and_deletion_requests.sql` into the migrations, and set the repository variables `APP_AUTH=on` and `SUPABASE_ANON_KEY`. The README lists each step.
- A delete request is stored in the database for the owner to act on. Deleting an account is done by hand for now.
