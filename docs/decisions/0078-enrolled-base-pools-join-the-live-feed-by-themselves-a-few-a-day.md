# Enrolled Base pools join the live feed by themselves, a few a day

## In plain words

The owner said yes on 2026-10-27: new Base pools that pass the data registry's checks now reach the public on-chain feed without anyone merging a change. Once a day a job checks each newly enrolled pool's depth again, adds at most three, runs the feed's tests, saves the change and deploys the live worker. One switch stops it.

## Context

[DEC-0064](0064-one-data-registry-finds-enrols-tests-and-watches-every-series-by-itself.md) made the registry find new Base pools and enrol them when their licence allows a public feed and they are deep enough. Going live still needed a hand edit of the feed's pool list ([DEC-0063](0063-the-public-sees-live-prices-from-our-own-on-chain-feed.md), [DEC-0065](0065-the-parity-price-combines-every-pool-the-way-pyth-combines-publishers.md)). The weekly discovery job rewrites that list from scratch and opens a pull request for a person to merge, so pools added to it by hand would be dropped by the next refresh.

## Decision

- Enrolled pools go in their own file, `web/live/src/venues/onchain-enrolled.json`, which the worker joins to the pool list when it loads (`withEnrolled`). The weekly refresh never touches it.
- `.github/workflows/pool-enrol.yml` runs `engine/src/parity/registry/feed.py` daily. It reads enrolled Base pools from `public.data_series`, measures each pool's depth now on a public Base node, and adds the ones that pass.
- Caps: the registry's depth bar (50k USD today), at most 3 new pools in any 24 hours, at most 8 pools per asset and 3 per chain (the same caps the discovery rule keeps), and only assets the feed already prices. A pool whose series is retired leaves the list. The viewers-per-feed cap is unchanged.
- When the list changes, the job runs the registry and on-chain tests, commits to main and starts the site deploy, which deploys the worker.
- Kill switch: the repo variable `POOL_AUTO_ENROL=off`.

## Consequences

- A new pool can be live within a day of enrolment, with no review. The caps and the fresh depth check are the guard; a bad pool also drops out of the price by itself, since the aggregate leaves out stale and outlying pools.
- The job pushes to main with the workflow token, so the normal pull request checks do not run for that one data file; the job runs the relevant tests itself first.
- A dry run on 2026-10-27 over the 17 enrolled Base pools added none: 13 belong to assets that already have 3 Base pools, 2 are USDT pools (the feed does not price USDT) and 1 is 48k USD deep, under the 50k bar. New pools will join as discovery finds them for other assets.
