# Addresses that do not exist get a real 404 and each app says not found

## In plain words

A mistyped or old link used to show the front page as if nothing was wrong. Now an address with nothing behind it shows a short page that says the page does not exist, with links to the front page and to search, and the server answers with the error code for a missing page (404). Inside each app, an unknown view shows the same kind of message with Back and Home buttons. A Verify badge link with no badge says so, also with a 404.

## Context

- Cloudflare Pages treats a site with no `404.html` at the top of its build as a single page app and answers every unknown path with the front page and status 200. Search engines then index junk addresses as copies of the front page, and people get no sign that the link was wrong.
- The apps (`/app/`, `/research/`, `/sim/`, `/trade/`, `/academy/`, `/lab/`) route by the part after `#` ([DEC-0015](0015-two-sides-a-product-app-and-a-research-app-kept-apart.md), [DEC-0038](0038-every-page-gets-its-tags-from-one-table-and-every-view-has-a-link.md)). An unknown hash fell back to each app's home view, except the Academy, which had its own message.
- `/v/<id>` served the badge page for any id with status 200 ([REF-0016](../reference/0016-parity-verify-mvp-spec.md)).

## Decision

1. **A static 404 page.** `web/404.html` is built into the root of the site build. Pages serves it with status 404 for any path that is not a file, a page or a function. It has no script, inlines the site's shared look, carries `noindex`, and links to the front page, to search (`/app/?search`, which opens the app's search box after signing in) and to the public glossary and trading ideas. The sitemap lists fixed pages only, so it stays out.
2. **Missing paths under an app folder open the app.** For a signed-in visitor, `/<app>/<x>` with no file behind it redirects to `/<app>/#/<x>`, keeping the query (`web/functions/_middleware.ts`). A real view opens (`/app/strategies` becomes `/app/#/strategies`); anything else shows that app's not found view. A signed-out visitor is sent to log in first, as before. Files, names with a dot and anything under `assets/` keep the plain 404. We chose a redirect over serving the app shell at the junk path because the apps read only the hash: the shell at `/app/x` would open the home view and hide the mistake.
3. **One not found view in every app.** `web/src/components/NotFound.tsx` shows the heading, a plain line, the address asked for, Back (the previous page, or Home when the tab has none) and Home. The product and research apps add Search. It is used for unknown hash routes in the product and research apps, Parity Terminal (a hash that is neither a workspace nor a product or research page), Parity Trade, Parity Academy (its old message) and Parity Workbench, and for a badge link with no badge.
4. **Badge pages.** `/v/<id>` still serves the badge page for every id, so the page can say what happened. It answers 404 when the id is not 12 letters and digits or when no badge has it. A failed lookup is not a missing badge, so it keeps 200.
5. **The dev server matches production.** `web/plugins/notFound.ts` answers page loads in `npm run dev` the same way: unknown paths get `404.html` with status 404 and missing app paths redirect to the hash. The rules live in `web/src/lib/notFound.ts`, shared with the middleware, and are covered by `web/tests/notFound.test.tsx` and `web/tests/middleware.test.ts`. The smoke test checks a junk path, a junk app path, a junk badge id and a junk hash in every app.

## Consequences

- Unknown addresses stop showing up in search as copies of the front page.
- Old path style links into the apps keep working when the view exists.
- A new app view needs its id in that app's list of views (`ROUTES` in `web/src/lib/space.ts` for product and research), or it shows not found.
- A new public page must be a real file in the build. There is no fallback any more.
