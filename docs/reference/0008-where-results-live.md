# Where results live and how they are tagged

## In plain words

Every official result is kept in four separate places, so losing one does not lose anything. Each copy is sealed so that a change shows up. Every result is also labelled with which idea it tests, which plan it followed, what kind of strategy it is and which markets it trades, and all of them are listed on one page.

## Summary

A result only counts if it is official ([DEC-0007](../decisions/0007-official-results-come-only-from-the-ledger.md)). This page lists where official results are stored, how we would notice if one changed or disappeared, and how they are labelled so they stay findable and meaningful.

## Four copies

| Copy | What it holds | How a change would show |
| --- | --- | --- |
| The ledger in git (`ledger/`) | Every official run, chained by hashes, plus a details file per run | `parity ledger verify` fails; runs in CI on every push, every night and every week |
| A GitHub release per run (`RUN-000001` and so on) | The full outputs, the ledger details and the exact data the run used | The weekly archive fails if any run is missing its release |
| Supabase | Every run's results and curves, readable on the dashboard | Rows can only be inserted by the nightly job, not edited; the weekly archive exports them |
| A weekly archive release (`archive-YYYY-MM-DD`) | Ledger, registrations, catalog, docs and CSV exports of the Supabase tables, with SHA-256 checksums | Checksums; and any week can be compared with the next |

Every clone of the repository (each of our laptops) is a fifth, informal copy of everything in git.

## How results are tagged

Each official result carries, automatically:

| Tag | Where it comes from |
| --- | --- |
| Run id, date, commit | The ledger entry |
| Plan (registration) and its pass criteria | `registrations/` |
| Hypotheses tested | The registration |
| Catalog entry, family and markets | The catalog entry whose `strategy` matches |
| Data fingerprint | The data snapshot hash recorded at run time |
| Outcome against the plan | The registration's pass criteria applied to the gauntlet |
| Trials counted | The ledger entry |

All of it is gathered on one generated page, the [results register](../RESULTS.md), and on the dashboard's Ledger page. Experiments and algorithm reports show the same numbers through generated results blocks, so the meaning (the experiment write-up) and the number (the ledger) always point at each other.

## Making results meaningful

A number on its own means little. Each official result must be readable as a sentence: "under plan REG-0003, testing HYP-0001, carry had a Sharpe of 0.41 against the market's 0.54 and failed its plan". That needs three things, which the routine enforces:

1. A hypothesis that says what we expected and why ([GDE-0004](../guides/0004-the-research-routine.md#the-pipeline)).
2. A registration that says what would count as success, written before the run.
3. An experiment write-up with threats to validity, written after.

## What could still go wrong

- If the owner's GitHub account were lost, the ledger and releases would go with it. The weekly archive should also be copied somewhere outside GitHub; Cloudflare R2's free tier would do. Not set up yet.
- The Supabase owner password could in principle rewrite rows. The ledger and releases are independent of it, so any rewrite would show up as a disagreement.
