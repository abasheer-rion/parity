# Architecture

## In plain words

A map of how the project fits together. Data comes in from free websites, gets saved, gets fed to each trading idea, the results get scored against the stock market, and the scores show up on the website.

## Summary

Data flows one way: free sources, then a local cache, then strategies, then one shared backtester, then a JSON report, then Supabase, then the dashboard. Each step can be run and checked on its own.

```text
FRED, Yahoo ──> engine/data (parquet cache) ──> strategies (weights)
                                                      │
                                                      v
dashboard <── Supabase <── report JSON <── metrics <── backtester (costs, carry, vol target)
(Cloudflare Pages)        (latest.json)
```

| `engine/src/parity/publish/` | Sends that document to Supabase. |
| `engine/tests/` | Tests on synthetic data, so CI never needs the network. |
| `web/` | The dashboard (Vite, React, TypeScript). |

| `.github/workflows/` | CI, deploys and the scheduled research run. |

## Backtest timing

Weights decided at the close of day t are held over day t+1. Costs are charged on every change in holdings. Currency positions earn or pay the interest rate gap each day. Volatility targeting uses only returns up to day t-1. These rules are tested in `engine/tests/test_backtest.py`.

## Automation

| Workflow | When | What it does |
| --- | --- | --- |
| `ci.yml` | Every push and pull request | Engine lint and tests, dashboard type check and build, docs check. |
| `deploy-web.yml` | Push to `main`, and pull requests | Builds the dashboard and deploys it to Cloudflare Pages. Pull requests get a preview URL. |
| `research.yml` | Weekdays at 23:30 UTC, or by hand | Fetches data, runs every strategy, uploads the report as an artifact and publishes it to Supabase. |
| `db-migrate.yml` | Push to `main` that touches `supabase/migrations/` | Applies new migrations to the Supabase project. |

## Database

Two tables hold results: `research_batches` (one row per run of the report) and `strategy_runs` (one row per strategy per batch, with metrics and weekly curves as JSON). A third, `members`, lists the emails allowed to read them. Only the scheduled job writes, as `parity_writer`, a database login that can insert results and nothing else. The dashboard reads with the public key after sign-in. Signed-in users can only read, and row level security only returns rows if their email is in `members`. Anyone can create a login, but a login that is not on the list sees nothing.
