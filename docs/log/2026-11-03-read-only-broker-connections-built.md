# Read-only broker connections built

## In plain words

On 3 November 2026 we built read-only broker connections for Verify, so a record can be marked broker-connected instead of self-reported ([DEC-0091](../decisions/0091-verify-reads-trades-from-brokers-with-read-only-keys-and-marks-the-record-broker-connected.md)). It is on in pull request previews and the test build and off on paritytrading.app until the owner sets the secrets and turns it on.

## What happened

- Connectors for Interactive Brokers, Alpaca, Coinbase, Kraken, Binance and Bybit, each written from the venue's official pages and tested against recorded answers in `web/tests/fixtures/connect/` (documented examples with made-up values; no real key is in the repository). Kraken's request signing is checked against Kraken's own published example.
- Every venue but Interactive Brokers and Alpaca has a call that says what a key may do, and the connector refuses any key that can trade, move or withdraw money. Interactive Brokers' Flex token can only fetch reports; Alpaca is reached through its sign-in with no scope, because its keys cannot be made read-only.
- Binance.US was dropped: its permission call answered 404, so a key cannot be proved read-only.
- The server signs each result; badges show as broker-connected only when the signature and every number check out. A withdrawn one keeps the venue and account code.
- Bybit's file layouts were checked against the real exports we could find. Its closed-positions file is now read; the two older layouts stay unverified.

## Decisions

- A key is used once by default; keeping it is opt-in, sealed and revocable.
- Tries stay the owner's to state; the methodology says so.

## Open questions

- What a real read-only Bybit key's permission lists contain (Bybit's own example is contradictory).
- Interactive Brokers' XML attribute names against a real XML statement.
- Alpaca's approval of Parity's app for other people's live accounts.
